# Forge evaluation matrix and release gate

This document defines the evaluation asset shipped with Forge. It is a
development and release contract, not a runtime feature. The machine-readable
matrix is [`addons/forge/evaluation/testdata/matrix.json`](../../addons/forge/evaluation/testdata/matrix.json); its fixtures are deliberately
synthetic and safe to run in CI.

## Offline contract gate

The fixture suite is deterministic and makes no provider, search, or embedding
call. The production gate is:

```bash
GOWORK=off make check
```

The focused evaluation gate is:

```bash
GOWORK=off make eval
```

`make check` already runs the package as part of the Forge module test loop;
`make eval` is explicit so a release log can show the evaluation result without
making the reader infer it from a larger test transcript. A fixture is an
external oracle: expected fields live in JSON and are not generated by the
code under test.

The matrix has a version and a falsifier for every case. A capability may not
be added to `FORGE.md` §11 without at least one case naming the fixture,
contract, and observation that would prove the policy wrong.

## Coverage

The current matrix covers the complete §11 capability list and the requested
evaluation axes:

| Area | Fixture-backed contract |
| --- | --- |
| topic, description, count, difficulty, style/mode | generation request and pack metadata |
| answer format | single-select and multi-select validation plus position mapping |
| source quality | recorded evidence remains unclassified until #120 decides policy |
| provider profile | the four V1 chat profiles decode their recorded wire replies |
| research | bounded SearXNG response fixture with injected retrieval time |
| verification | an answer-key mismatch is rejected before acceptance |
| repair | one corrected candidate is re-verified and accepted |
| failure | shortfall and near-duplicate cases fail closed without a draft |
| provenance | generation spec, provider/model, verifier, source ref and confidence survive |
| migration | Forge tables use their own registry and leave core table definitions unchanged |
| review flow | acceptance calls the import port before removing the draft |

The matrix does not decide D-022's calibration policy, #120's source policy,
#105's style vocabulary, or the mechanism of `Gate.Apply`. It gives those later
decisions a stable fixture seam and does not import evaluation cases into live
prompts.

## Scoring rubric for selected live cases

The live/manual lane is run only for selected matrix cases after a material
prompt, model, threshold, or release change. The rubric is registered before
the run. Each dimension is scored per accepted question from 0 to 2:

| Dimension | 0 | 1 | 2 |
| --- | --- | --- | --- |
| factual correctness | a claim is false | materially incomplete or uncertain | every claim is supported by the evidence and correct |
| answer-key correctness | marked answer is wrong | answer is defensible but ambiguous | exactly the marked answer(s) are correct |
| grounding/source use | no supporting source | source is cited but only partly supports the claim | every material claim is supported by cited evidence |
| structural validity | cannot be imported | imports after a manual correction | imports unchanged and satisfies the pack contract |
| distractors | absurd, misleading, or partly correct | plausible but uneven | plausible, definitely wrong, and useful for assessment |
| diversity | duplicate or same fact as another case | overlap without a duplicate | distinct concept and competency within the requested topic |

Hard pass conditions are structural validity, answer-key correctness, and
grounding at 2 for every accepted question. The mean distractor and diversity
score must be at least 1.5, with no zero. A failure case passes only when the
expected refusal, no-draft result, and safe diagnostic all hold; a smaller
successful pack is not a pass.

Similarity thresholds are evaluated separately against the labelled fixture
pairs and a provider/model-specific calibration record. The lexical fixture
baseline is a derivation check, never a production threshold (D-022).

## Redacted live/manual record

The manual lane records only this safe shape, outside the fixture inputs:

```json
{
  "matrix_version": "forge-evaluation-0.1.0",
  "case_ids": ["rich-generation-request"],
  "provider": "<safe provider id>",
  "model": "<safe model id>",
  "embedding_model": "<safe model id or none>",
  "cost": {"input_tokens": 0, "output_tokens": 0, "currency": "<provider or none>"},
  "outcome": "pass|fail|inconclusive",
  "diagnostic": "<short redacted outcome>",
  "secrets_recorded": false,
  "raw_prompts_recorded": false,
  "raw_model_output_recorded": false
}
```

Provider/model identifiers, token or cost summaries, and pass/fail outcomes are
safe evidence. Credentials, endpoints, account identity, topology, raw
prompts, copied pages, and raw model/tool output are not. A public issue or
release note receives only the redacted record; private deployment details stay
with the operator. A local Ollama run records zero provider currency cost, not
an omitted cost.

At release time:

1. Run `GOWORK=off make check` and `GOWORK=off make eval` on the clean release
   candidate.
2. Run the selected live cases against the operator-managed deployment and
   record provider/model, embedding model where applicable, token/cost
   summary, outcome, and concise diagnostic in the shape above.
3. Score accepted questions with the registered rubric. Record an
   inconclusive result when a provider or model cannot complete the case;
   never turn an unavailable measurement into a pass.
4. Keep the live evidence redacted and verify that no raw prompt, raw output,
   credential, or private endpoint entered the public record.

The release procedure does not make live calls from `make check` or `make eval`.
The hard V1 live-review requirement remains the separate #130 gate.
